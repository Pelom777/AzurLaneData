## CDN 清单是全量库存，不是单次热更的增量（实测证据）

用户的质疑：「热更包只有一次更新的内容，一年缺席很多次热更，缺失资源是不是在客户端里？」

结论：**清单是全量快照，不需要 APK，也不受"漏了中间热更"影响。**

- 旧仓库（2025-06-06 快照）的 **2,159** 个 painting 目录，在当前 9.7.398 的 painting
  清单里 **2,159 个全部仍在（100.0%）**，被删的 **0**。若是增量清单，这个数字应为 0。
- 当前 painting 清单 **10,773** 条（去 `_tex` / `-mesh` 依赖后 **6,700** 个基础名），
  是旧仓库 2,159 的 **3.1 倍** —— 四年积累的库存，不是一年的增量。
- 当前数据引用的立绘 **2,491** 张，CDN 清单里 **一张不缺（缺失 0）**。
  `used` 集合是 2,911，多出的 420 全部来自 `equip.json`，是装备图标名
  （走 `equips/` 命名空间，不在 painting 清单里，但 equipicon 清单命中 420/420）。
  所以 **2,911 − 420 = 2,491** 完全闭合。
- 每个域的清单由独立版本号驱动（`painting 0.0.1802` / `az 9.7.398` 等），
  逐文件带 md5 —— 客户端要靠它校验全部文件的完整性，设计上不可能是增量。

## 对决策的影响

用户这个质疑反而**强化了"可生成类全量重生"**的理由：全量重生唯一的悬念是
"原料是否齐全"，而实测答案是齐全（2,491/2,491）。且这一年 painting 域**没有资源被删**。

## 真正不可恢复的一类（口径要说清）

资源若在中间某次热更上线、后来被删（联动到期/下架/重做），既不在当前清单、
也不在旧仓库（停在 2025-06 之前），则无法获取。量级不可估（不在任何可读清单里），
但不影响站点 —— 当前数据表也不引用它们。

## 单船端到端示例跑通（白凤 / baifeng）

## 决策：painting 走 CI 全量重生

用户要求：`painting` 全量重生必须在 GitHub Actions 上跑、注意时长与容量，
且「这段代码以后更新时也要能用」——即不能是一次性脚本。

### 新文件路径
- `.github/workflows/regen-assets.yml`（3 个 job：prep / regen×N / merge）
- `scripts/azl_assets.py` 新增 `--shard I/N`（crc32(名字) 分桶，不用 hash()，后者按进程随机化）

### 三个必须记住的设计点（任缺其一就会退化成一次性脚本）
1. **每个分片继承基线 state**（`cp .azl/assets-state.json .azl/state-N.json`）。
   从空 state 起手 ⇒ 每轮 dispatch 都全量重解。
2. **配合 `mark_remote`** 把远端对象翻译成 marker，让「产物在磁盘」在干净 checkout 里成立。
3. **刻意不加 `--seed`** —— seed 在「远端有 / state 无」时跳过，等于把
   「托管那份就是最新版」这个不可验证的假设写进 state（见下）。

### state 合并规则（最容易写错）
每份片段都含整份基线的照抄值 ⇒ 按文件名顺序 union 会用**旧基线值**覆盖
前面片段刚算出的新值。必须按 key 做差分：只应用「与基线不同的那个值」；
多个冲突值则保留基线并告警。已用 4 个场景离线单测（含「无片段时拒绝合并」）。

### 为什么弃用 `--seed`（用户追问「你是否知道缺哪些」后推导出的）
`prev[key] = info['md5']` 记的是**当前 CDN 的 md5**，但磁盘上的字节来自
2025-06-06 的旧快照。两条实测把这个前提否掉了：
- CDN 清单是**全量文件表**不是补丁列表：旧仓库 2025-06 的 2,159 个立绘
  在当前 painting 清单里 **100% 还在**；当前清单 6,700 个基础名 = 旧仓库的 3.1 倍
- 当前数据引用的 2,491 张立绘，CDN 清单里**一张都不缺**

### 实测数据
- 体积：painting used = 2,491 张 / 下载 3.7 GB / 产物 5.6 GB
- 单 job 峰值约 9.3 GB，runner `/` 只有 ~14 GB ⇒ 必须分片（6 片时每片 ~1.6 GB）
- 预算：6 片并行约 20 分钟，Actions 配额约 130 分钟/次全量

### 事故：merge job 的提交静默丢失

日志打印 `推送失败（1/3）` → `已推送到 main`，但远端 main 没有这个提交。
三种方式交叉核验（`ls-remote` / `contents?path=` / `commits?path=`）都证实。

**确定无疑的缺陷**：`common.commit_and_push` 把 `git push` 返回码 0 当成功，
而 git 在「远端已包含 HEAD」时打印 `Everything up-to-date` 也返回 0 ——
无法区分「推上去了」和「我的提交在 pull --rebase 里被丢掉了」。
长任务（30 分钟）期间 main 被推进 → 必踩。

**加固**：新增 `common.pushed(branch, cwd)`，推后 `ls-remote` 回读远端 tip
比对本地 HEAD，不一致则告警重试，三次不过 `die()` 让这一轮变红。

**恢复**：6 份 artifact 按差分规则合成回填 → `73353c8`，state 2,499 条
（painting 2,491 + squareicon 8）。

### 压缩效率实测（12 张 painting + 12 个 paintingface 样本）

**结论：不划算，未改流水线。** 数据如下（比例 = 编码后/原始）。

| 方案 | painting 压缩比 | paintingface 压缩比 | 编码ms/张 | 可见区最大像素差 | 前端改动 |
|---|---|---|---|---|---|
| PNG 重新优化 l9 | 0.948x | 0.948x | ~1400 | 0 | **零**（扩展名不变）|
| webp 无损 m4 exact | **0.658x** | 0.630x | ~2600 | **0** | 6 处 URL |
| webp 无损 m6 exact | 0.641x | 0.614x | ~19700 | 0 | 6 处 URL |
| webp 无损 m4 默认 | 0.618x | 0.611x | ~2700 | 0（但透明区 255）| 6 处 URL |
| webp 近无损 80 | 0.607x | 0.612x | ~1700 | 0（但透明区 255）| 6 处 URL |
| webp 有损 q85 | 0.138x | 0.154x | ~4900 | **138** | 6 处 URL |
| avif q100 | 0.486x | — | ~580 | **117** | 6 处 URL |

两条容易踩的：

1. **「无损」不等于像素一致。** libwebp 默认无损会把全透明像素的 RGB 归一化换压缩率，
   实测最大差 255。必须 `exact=True`（Pillow）/ `-exact 1`（cwebp），
   代价约 4pp 体积。
2. **Pillow 的 AVIF 根本没有无损档。** `quality=100` 按 libavif 约定应是
   AVIF_QUALITY_LOSSLESS，但实测可见区最大差 73~117 —— 它是有损的。
   真无损 AVIF 得换 `avifenc` 二进制，等于给 CI 加依赖。

**否决理由**：唯一真实收益是腾出 3.3 GB 给 spine，但 spine 是 2025-06 旧快照、
与现在全量重生的 painting 版本本来就齐不了；换来的却是 34% 编码 CPU、
前端 6 处拼接改动、以及一个**只在贴图集上暴露且不报错**的渗色风险。
PNG 重新优化虽零风险，但只省 5.2%，意义不大。

### exact=True 的无损 WebP 是否「效果无区别」（2026-10-22 追问）

**像素层：能证明。** 30 张真实立绘 + 7 个合成边界用例，全部逐字节一致：

| 用例 | 结果 |
|---|---|
| 30 张真实立绘（最大 2048×2048，全 RGBA） | 30/30 差异字节 = 0，压缩比 **0.663x** |
| 调色板 P / 1×1 / 4096×4096 / 全透明+随机RGB | 全部 0 差异 |
| 带 ICC 的图 | ICC 被写进 `ICCP` 块，保住 |
| 带 gAMA 的图 | **gAMA 丢失**（WebP 无对应块） |

**三关，过了两关：**

| 关 | 结论 |
|---|---|
| 像素 | ✅ 已实测 |
| 元数据 | ✅ 我们的 PNG 只有 `IHDR/IDAT/IEND`，没有 gAMA/sRGB/iCCP（cv2.imwrite 不写）——所以不存在偏色。但 WebP 格式本身存不了 gAMA，若将来源自带 gamma 会翻车 |
| 浏览器 | ❌ 不支持 WebP 的设备直接裂图，`exact` 管不了 |

其他硬指标：最大边长 2048×2048，WebP 上限 16383，够用 8 倍。

### 重构：sync-assets + regen-assets 合并为 update-assets.yml

用户问「全量脚本和热更新脚本能否统一逻辑」。答案是能，而且**必须**，
因为两者不只是重复，是**语义相反**：

| | `--seed` | 远端有、state 无记录时 |
|---|---|---|
| 旧 sync-assets | 传了 | 跳过（断言远端=最新） |
| 旧 regen-assets | 刻意不传 | 重新生成 |

同一个 state 文件在两个入口得出相反结论。现在统一为 `update-assets.yml`：
- `shards` 默认 **1**（热更新），全量用 6 —— 这是唯一真正的差异
- `seed` 默认 **false**，只作为「一次性迁移存量资产」的显式开关
- 分片账目改成 artifact 里的 `report-N.json`，merge 汇总后写进提交信息
- `shards=1 && force=true` 会打 warning（否则全量压一个 job 要跑两小时）

**代价**：热更新多两个 job（prep ~5s + merge ~40s），单次慢约 45 秒。

本地已验两处关键逻辑：
1. heredoc 渲染出的 `report-N.json` 是合法 JSON
2. merge 差分合并：基线 {k1,k2}，片段 A 加 kA、片段 B 把 k2 改 NEW
   → 结果 {k1, k2=NEW, kA}，**没被其他片段照抄的旧值覆盖**；账目 5+3=8 正确

**CI 冒烟已通过**（run `39723185349`，squareicon / shards=1 / limit=3）：
prep 3/3、assets 18/18、merge 10/10 全绿；片段 1 个应用 3 条，state 2502；
提交信息 `assets: 新增 3 / 变更 0（1 片）` —— 账目跨 job 传递成功；
`pushed()` 回读校验也在日志里留下了「已回读远端校验」。
→ 说明 `shards=1` 退化成单路、账目 artifact、推后校验三者都真的生效了。

### 第二次踩到「提交静默丢失」，根因变了

这次是 `update-data`（run `39725189756`）：日志 `已推送到 main（已回读远端校验）`，
但远端没有该提交。**上次加的 `pushed()`（ls-remote 比对 HEAD）没用**，因为
`git pull --rebase` 把提交丢掉后 **HEAD 被挪到远端位置**，`HEAD == origin/main`
依然成立 —— SHA 比对天生分不出「推上去了」和「提交没了」。

| 实际情况 | push rc | HEAD == 远端 |
|---|---|---|
| 推上去了 | 0 | 是 |
| 提交被 rebase 丢掉 | 0 | **也是** |

**修复**：新增 `common.landed(cwd, branch, snapshot)`。提交后、推送前记下每个目标
路径的 `tree/blob sha`；推送后回读 `origin/<branch>:<path>` 比对，内容对上才算真的到了。
`--paths-from` 模式没有目录粒度，退回 SHA 校验并告警（目前无人使用）。

本地用裸仓库验了两种情形：远端内容已变 → False；正常竞争（远端前进 + 本地提交 →
rebase → 推送）→ True 且远端确实有该文件。

**遗留**：这次丢的是 data 提交（R2 已是 9.7.410，git 里还是 9.7.398）。
下一轮 update-data 会发现 version.json 没前进 → 重新解包 → 重试提交。

### 决策：_ex 用内联布局（写进本体目录），前端零改动

用户问「改成和本体同级（独立目录）前端改动大吗」。答案：6 行（`profile/index.vue`
里 `loadPainting` 加一个 dir 参数 + 2 处模板串 + handleChange 里算 dir）。

但证据表明**没必要**，内联更好：

| | 内联（选定） | 独立目录 |
|---|---|---|
| 前端改动 | **0 行** | 6 行 |
| 新增体积 | 每个 3 文件（json + rw_ex png + mesh） | 再复制基底+正面贴图，约 3.3 MB/张，8 张约 24 MB |
| 覆盖风险 | 无（见下） | 无 |

关键证据：8 个 `_ex` 包的 externals 全部指向**本体的** `<name>_tex` /
`<name>_front_tex`，外加自己的 `<name>_rw_ex_tex`。即 `_ex` 包**没有自己的
基底贴图**，写出来的 `yan.png` 与本体重绘逐字节相同（实测 md5 前后一致），
覆盖是空操作。代码里仍留兜底：写前留底，写完字节变了就还原 + warn。

三个实现约束（写进 docs/CDN.md §4.10）：
1. 包内基底层叫 `<name>_ex`，但 json 的 key 必须写回本体名 —— 前端
   `loadPainting` 用的是 `json[name]`，写成 `yan_ex` 会读到 undefined 整张崩。
   `PaintingExporter` 新增 `base_key` 参数承担这个映射。
2. `_ex` 不在引用集里，要跟随本体：先剥 `_ex` 再查 used。
3. `base_names` 用清单里真实存在的立绘集合，所以 `yan_n_ex` 归到 `yan_n`，
   不会凭空造路径。

范围：15 个 `_ex` 条目里 8 个本体在 used（banjiu / feiniao / gaoxiong_6 /
xishao / xuebugui / xuequan / yan / zi_shanluan），盘点出 8 个待处理。
