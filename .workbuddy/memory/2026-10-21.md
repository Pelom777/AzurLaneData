## azhash 判据调研（未落地，结论备查）
问：能否改用游戏版本号或握手 hash。实测握手返回 10 个资源域：
`az 9.7.398 / painting 1802 / l2d 1590 / cv 1481 / cipher 1304 / bgm 1300 / dorm 1551 / manga 1342 / map 333 / pic 1312`。
- **客户端版本号不可用**：APK 名叫 `blhx_9.7.25_0828_1_20260920_104023_5af08.apk`，
  9.7.25 构建于 2026-09-20，热更不动 APK → 整个 10 月的更新对它隐形。
- **hash 段 vs 整串**：`$azhash$9$7$398$def4c26318af25f3` 整串就是清单 URL 路径
  （`/android/hash/<整串>`），版本段和 hash 段同生共死，只比 hash 语义略准但零收益，不值得动。
- **真问题是误报**：azhash 是**全量**资源指纹，纯图片/语音热更也会变，
  而 cache key 是 `lua-CN-<stamp>` → 一变就 miss → 冷缓存 1265.9s 白跑。
- **可选的二级精筛**：az 清单实测 4,147,712 字节 / 64,649 条 / 1.1s，**逐文件带 md5**；
  我们只关心 33 条（`sharecfgdata/*` 32 张 + `scripts32,39737983,673376f1a749f726f0757de729a1000e`）。
  指纹没变即可跳过解包。坑：azhash 变但数据没变时若不写 state，会每小时重拉 4MB。
- 用户跳过决策，代码未改。

## 勘误：azhash 变化 ≠ 冷缓存
我先前说「azhash 一变 cache key 就 miss → 白跑 1265.9s」，**漏了 `restore-keys`**。
`update-data.yml` 里精确 key 是 `lua-CN-<stamp>`，但紧跟 `restore-keys: lua-CN-` 前缀回退，
所以 azhash 变化时会命中上一版缓存，只有 md5 真变的那几张表需要重解。
已知的两个端点：`50.5s`（force + 精确命中）与 `1265.9s`（真冷缓存），
「热更打断 + 前缀命中」这条中间路径尚未实测，不要拿 1265.9s 当热更的常规代价。

## 缺口：sync-assets 没有自动触发
`sync-assets.yml` 注释写「由 update-data 的版本变化或人工 dispatch 触发」，
但 `on:` 只有 `workflow_dispatch`，update-data 里也**没有任何** `gh workflow run` /
`repository_dispatch` / `workflow_run`。即热更后图片不会自动同步，必须手动点。
